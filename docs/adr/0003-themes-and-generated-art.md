# Themes and generated art

The portfolio gets its own look ("Inside the machine") instead of the borrowed Freedoom art, and the visitor can choose between more than one look. We split theming into two levels. An art set is everything the game draws and plays: the textures a Level may name, the Bug walk and fix frames, the sound file of each sound event, and the HUD colors. A Theme is a named look of the whole portfolio: an art set plus a look for the HTML screens, chosen with CSS on the root `data-theme`. Paper and Board are two Themes on one machine art set; a later Theme (Dungeon) brings its own art set.

The art set lives in one module of the game layer (`src/game/theme.ts`), with no imports, so the Title Screen can read the Theme ids without game code. The browser shell, the Bugs, the HUD, and the Audio read the art set instead of their own constants, and `createGame` fails when the Level names a texture, or needs a Bug frame, that the art set does not have, so `pnpm test` catches a missing asset. The engine never sees the art set (ADR 0001).

The machine art is generated: a script under `scripts/` draws the textures, Bug frames, and posters, and synthesizes the sounds, from code with a fixed seed and only Node built-ins. We chose generated art over hand-drawn or licensed art because it is original, reproducible, and free of license questions, and a new Theme needs only new drawing code and CSS. We accept that procedural art is simpler than hand-drawn art. The generated files are committed, so the build has no generation step.

## Amendment: the Theme head script on the Skip View

The Skip View was a page with no script of ours, so it could never show a saved Theme: a visitor who chose Board saw Paper there on a light system. Now the Skip View runs one inline head script, and that script only sets the saved Theme as `data-theme` on the root. The `theme-script` plugin in `vite.config.ts` puts the same script (`src/theme-script.ts`) into the Title Screen, after the phone redirect, and into the Skip View. Its list of accepted Theme ids is built from `THEMES` at build time, so a new Theme cannot be missing from a page. The script has no game code, and the Skip View works fully without it: with script blocked, or with no saved Theme, the system setting chooses Paper or Board.

## Amendment: texture roles

A Level named machine texture files (`board-a`, `chip`, ...), so a second art set could not reuse it. Now a Level names texture roles, not files: `wall-a`, `wall-b`, `feature`, `storage`, `door`, and `door-track` (`TEXTURE_ROLES` in `src/game/theme.ts`). Each art set maps every role to one of its own files, and gives the poster of each Exhibit at `<posters folder>/<Exhibit id>.png`, so the Content names no poster. One Level works with every art set, and `createGame` (and `game.changeArtSet` during play) fails when an art set has no file for a role, or when the Level names a texture that is not a role. We accept that a new kind of wall needs a new role in every art set, not only a new file.

## Amendment: the dungeon art set

The Dungeon Theme brings its own art set, as planned: a torch-lit stone keep in `public/dungeon/`, made by a second generator, `scripts/dungeon-art.ts`, with the same rules as the machine one (fixed seeds, Node built-ins only, committed files, a `Software` or `ISFT` text that names the generator). The two generators share their file writers, pixel and sound helpers, and the Bug frame and poster builders in `scripts/art-kit/`. The generator also draws the files of the Dungeon HTML look (the pulp and weave tiles, and the ink plate of the Title Screen), so every PNG and WAV of the Theme names the same generator. The torch light is baked into the torch texture: the engine gets no lighting (ADR 0001). The visitor can change the Theme during play from the Pause Menu; the old art set stays until the new one has loaded and passed its check.
