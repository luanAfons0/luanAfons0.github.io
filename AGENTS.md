# Portfolio

A Doom-inspired first-person game, written in TypeScript with Vite, that presents Luan's portfolio. Read `GLOSSARY.md` and use its terms.

## Commands

Use pnpm. `pnpm dev` (dev server), `pnpm build` (type check, then Vite build), `pnpm typecheck`, `pnpm lint` (Biome check), `pnpm format` (Biome fix), `pnpm test` (Vitest, one run), `pnpm size` (gzipped JS budget of 100 KB; run after `pnpm build`), `pnpm bench` (render benchmark, 60 FPS target). Before you commit, `pnpm typecheck && pnpm lint && pnpm test` must pass.

## Commits and pull requests

Commits follow [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/):

- Subject: `<type>(<scope>): <summary>`. English, imperative, lowercase, no period, 72 characters or less. Types: `feat`, `fix`, `refactor`, `perf`, `test`, `docs`, `build`, `ci`, `chore`, `style`. The scope is optional and names the area: `engine`, `game`, `skip-view`, `title-screen`, `audio`, `analytics`, `assets`, `ci`. Mark a breaking change with `!` after the type or scope.
- Body (optional): why the change was made, wrapped at 72 characters.
- Footer: one `Closes #<n>` line per issue the commit finishes.
- The message describes only the change. It has no `Co-Authored-By` trailer and no AI attribution.
- One logical change per commit.

Pull requests:

- Branch from `main` as `<type>/<short-slug>` (for example `feat/exhibit-panel`). Base is `main`.
- Title: the Conventional Commits subject format, in English.
- Body: in English. One summary line, then one `-` bullet per change, naming the exact file, function, or behavior that changed (for example "Exhibit `id` validation in `content.ts`"). Then one `Closes #<n>` line per issue. Same attribution rule as commits.
- Label `enhancement`, assignee `@me`.
- Merge only when CI is green, with a merge commit (`gh pr merge --merge`), so each commit's `Closes #<n>` stays in the history.

## Code layout

- `src/engine/`: the generic raycaster (Renderer, Collision, Loop, Input). It never imports `src/game/`; a Biome rule enforces this (ADR 0001).
- `src/game/`: the portfolio. `game.ts` is the Game core (test Seam 1): no DOM, no canvas, no timers.
- `src/skip-view/`: the Skip View builder (test Seam 2, `buildSkipView`). It runs at build time only: the `skip-view` plugin in `vite.config.ts` turns `skip/index.html` into the Skip View, from the Content and the Level. The built page has no game code. Its only script of ours is the Theme head script, and the page works fully without it. Only the `goatcounter` plugin in `vite.config.ts` adds the GoatCounter tag to both pages, in the production build only.
- `index.html` is the Title Screen: plain HTML and CSS, plus two inline head scripts that run before the first paint: first the phone redirect, which sends phones to the Skip View (ADR 0002), then the Theme head script. The `title-screen` plugin in `vite.config.ts` puts the Features counts (Rooms, Exhibits, Bugs) from the Level and the options of the Theme select (one per id in `THEMES`, named by `THEME_LABELS`, at `<!--theme-options-->`) into it, through `titleScreenPage` (`src/title-screen/page.ts`). Its entry, `src/title-screen/main.ts`, has no game code: `createTitleScreen` (`src/title-screen/title-screen.ts`, tested with happy-dom on the real `index.html` markup) loads the game with a dynamic `import()` on hover or focus of NEW GAME. Its `onNewGame` hook is the NEW GAME user gesture: start the Audio there. `createTitleScreen` sends the `new-game`, `skip`, and `theme/<id>` analytics events itself.
- `src/theme.css`: the shared stylesheet of every HTML surface: the faces (self-hosted in `public/fonts/`, each with its OFL license: Archivo and Silkscreen for Paper and Board; IM Fell English, IM Fell English SC, Alegreya, and Alegreya SC for Dungeon), the palette, and the look tokens of the Themes. A saved Theme is `data-theme` on the root; with none, `prefers-color-scheme` chooses (light gives Paper, dark gives Board; Dungeon has no system trigger). The look sets `color-scheme`, so look tokens use `light-dark()`. Use `.only-paper`, `.only-board`, and `.only-dungeon` to show an element in one look. The Dungeon look (`color-scheme: light`, one look) has its own palette (`--dungeon-cover`, `--dungeon-page`, `--dungeon-ink`, and the others), faces (`--font-fell`, `--font-fell-sc`, `--font-book`, `--font-book-sc`), and lining figures on every element; the shared look tokens (`--surface`, `--text`, ...) take its ink and pulp. Write every Dungeon rule under `:root[data-theme="dungeon"]` or on an `.only-dungeon` element, and put the page grounds on with `.dungeon-pulp` and `.dungeon-cover` (the pulp and weave tiles of the dungeon generator), so that Paper and Board never fetch a Dungeon face or tile.
- `src/main.ts`: the browser shell (canvas, `requestAnimationFrame`, keyboard), loaded lazily. `loadArt(artSet)` loads and decodes the art of an art set once (then from a cache), and `startGame(artSet, audio)` runs the game with an art set whose art is loaded. The Title Screen entry (`src/title-screen/main.ts`) calls both with the art set of the shown Theme; `createTitleScreen` calls `loadGame` again after a Theme change, so the loaded art always matches the shown Theme. During play, the Theme switch of the Pause Menu calls its `onThemeChange` hook: for a Theme with another art set, the shell runs `loadArt` (the current art stays until it ends), then `game.changeArtSet` and `audio.changeArtSet`; a switch between Paper and Board changes nothing. When the load or the check fails, the hook rejects, and the Pause Menu sets the Theme back and shows one line until the next Theme choice (a stale failure, after a later switch, is ignored). After NEW GAME, the Title Screen keeps the Theme until the game starts or fails to load. The Pause Menu owns the settings during play: the shell applies and saves what `onSettingsChange` reports, and M calls `pauseMenu.toggleSound()`. Manual test only. Never import it statically from the Title Screen.
- Tests sit next to the code as `*.test.ts` and go through a seam: `createGame` for Seam 1, `buildSkipView` for Seam 2. Build test Levels with `src/game/test-support/tiled-level.ts`.
- Tiled Levels are in `src/game/levels/`. Biome does not format them, so Tiled can write them.
- Tiled wall tiles name their texture role with a `texture` tile property (and a door tile names the role of its side walls with `track`), in a tileset embedded in the Level. The texture roles are `TEXTURE_ROLES` in `src/game/theme.ts`: `wall-a` and `wall-b` (two plain walls), `feature` (the feature wall: the chip, or the torch), `storage` (the storage wall: the rack, or a shelf), `door`, and `door-track`. A Level never names a file of one art set, so one Level works with every art set. The tile `image` paths only show the tiles in Tiled.
- Tiled Bugs are point objects of type `bug`. Each one must be inside a Room rectangle, where it walks.
- `src/game/content.ts` is the Content: the one typed list of Exhibits. Tiled places each Exhibit as a point object of type `exhibit` inside a wall cell, with an `id` property and a `facing` property (`north`, `east`, `south`, or `west`: the side of the wall the poster is on). Creating the Game core fails when the Level and the Content do not match, so `pnpm test` catches it. The Content names no poster: the poster of an Exhibit is `<posters folder>/<Exhibit id>.png` in each art set (`posterPath` in `src/game/theme.ts`). The generator draws one poster per Exhibit with its Part label, so a new Exhibit needs a generator run.
- `src/game/theme.ts`: the Themes and the art sets (ADR 0003). It has no imports. An art set names the folder of each kind of file (`folders`: textures, sprites, posters, sounds), the file of each texture role (`textures`), the Bug frames, the sound file of each sound event, the ceiling and floor colors, and the HUD colors; the browser shell, the Bugs, the HUD, and the Audio read it. `createGame` with `artSet`, and `game.changeArtSet` during play (it keeps the player, the Bugs fixed, the doors, and the open Exhibit, and keeps the old art set when its check fails), fail with an error that names the art set and the missing item when the art set has no file for a texture role, no sound for a sound event, no image for a Bug frame (in `sprites`), or no poster for an Exhibit (in `posters`); it also fails when the Level names a texture that is not a texture role. The machine art set (the Paper and Board Themes) takes every file from `public/machine/`: wall textures (the roles map to `board-a`, `board-b`, `chip`, `rack`, `door`, `door-track`), Bug frames with their anchors in `sprites/offsets.json`, posters, and sounds. The dungeon art set (the Dungeon Theme) takes every file from `public/dungeon/`: the roles map to `stone-a`, `stone-b` (moss), `torch`, `shelf`, `door`, `door-track`; the Bugs are Slime frames; the posters are banners. `artSetOf(theme)` (the map `THEME_ART_SETS`) is the only place a caller gets an art set; no Theme (the system look) gives the machine art set. A new Theme with its own look but the same game art adds its id to `THEMES`, maps it in `THEME_ART_SETS`, and adds its look to `src/theme.css`; a Theme with other game art also needs its own art set.
- `scripts/art-kit/`: the shared module of the art generators. `files.ts` has `fileWriters(generator)`, which gives the PNG writer (with the `Software` text chunk) and the WAV writer (with the `ISFT` text), `writeFiles`, and `SAMPLE_RATE`. `pixmap.ts` has the `Pixmap` and its pixel helpers (`flash` is the hit frame of a Bug). `kinds.ts` has `bugFrameFiles` (the Bug frames and `sprites/offsets.json`) and `posterFiles` (one poster per Exhibit). `synth.ts` has the sound helpers. `read-files.ts` (`readPng`, `sameContent`) reads generated files, for the generator tests only. Import from it; do not copy it.
- `scripts/machine-art.ts`: draws and synthesizes the machine art set into `public/machine/` with fixed seeds and Node built-ins only; each PNG names the script in a `Software` text chunk. Each asset kind is one module under `scripts/machine-art/` (`textures.ts`, `bugs.ts`, `posters.ts`, `sounds.ts`), listed in `KINDS`. Sounds are synthesized as 16-bit mono WAVs whose `ISFT` text names the script. After a change, run `node scripts/machine-art.ts` and commit the files; `scripts/machine-art.test.ts` fails when the committed files are out of date (it compares PNGs by image data and text) or when the folder has a file the generator does not write.
- `scripts/dungeon-art.ts`: the same for the dungeon art set, into `public/dungeon/`, with its modules under `scripts/dungeon-art/` (`stone.ts` draws the cut stone that the textures and the banners share; `tiles.ts` draws the pulp and weave tiles of the Dungeon HTML look into `tiles/`, which `src/theme.css` uses). The drawings port the approved mock's `dungeon-frame.js` (removed after the build; it is in commit 2487e66). Run `node scripts/dungeon-art.ts` after a change; `scripts/dungeon-art.test.ts` checks the committed files.
- The Theme setting: the visitor picks a Theme with the Theme item of the Title Screen or the Theme switch of the Pause Menu. The Theme item is a label and a native `<select>` (`data-menu-item="theme"`), the third menu item: its value is the shown Theme (it follows the system look while no Theme is saved), and a change switches the Theme and makes the next load of the game use the new art set. With the select focused and its picker closed, the arrow keys move the menu selection (not the value), and Enter or Space opens the picker (`showPicker()`, else the browser default); a click on the row opens it too. It is `disabled` from NEW GAME until the game starts or fails to load. Both save `theme` in the settings (`src/game/settings.ts`, `localStorage` key `portfolio.settings.v1`) and set `data-theme` on the root at once. The Theme head script (`src/theme-script.ts`) reads the saved Theme before the first paint and sets `data-theme` on the root. The `theme-script` plugin in `vite.config.ts` puts it into both pages, at the `<!--theme-script-->` mark (in `index.html`, and written by `buildSkipView`), and fails the build when a page has no mark. Its accepted ids are built from `THEMES` (ADR 0003), and it reads the key `SETTINGS_STORAGE_KEY` of `src/game/settings.ts`.

## Title Screen look

`index.html` has one markup for every Theme. In Dungeon it is an open gamebook: the `.only-dungeon` left page (`.title-screen__leaf`: running head, the ink plate, How to Play, folio) and the right page (the shared name, description, and menu items, plus Dungeon-only stat boxes, leaders, hints, and manicules). The rules are the last section of `src/title-screen/title-screen.css`. The loading die and the error stay in the menu figure in the markup; CSS anchor positioning (`--title-plate`) puts them under the plate in place of How to Play. The ink plate (`public/dungeon/title/ink-plate.png`, lazy `<img data-ink-plate>`) comes from `scripts/dungeon-art/plate.ts`, a port of the mock's `renderInkPlate`; the NEW GAME dive grows from it (the dive source of each Theme is `diveFrom` in `title-screen.ts`). `createTitleScreen` steps the die (`[data-die]`) every 140 ms while the loading state shows, except under reduced motion. `titleScreenPage` fills the stat boxes from the Level (`<!--level-rooms-->`, `<!--level-exhibits-->`, `<!--level-bugs-->`) and the Theme options (`<!--theme-options-->`), and fails when a mark is missing. In Paper, Figure 1 (`.title-screen__chip`, a 6-pin chip: pins 1 to 3 are the menu, pins 4 to 6 are NC) holds only the menu, and Table 1 (`table.title-screen__controls`, `.only-paper`) lists the controls under it. `.title-screen__chip` is `display: contents` in Board and Dungeon, so their layout does not change. The Theme select reads as item text (`appearance: none`, or `appearance: base-select` where the browser has the customizable select); the selection marker, hover, and focus ring are on its row (the `<label class="title-screen__item">`), and `.title-screen__caret` draws a pixel caret in Paper and Board and an ink caret in Dungeon. With `base-select`, each Theme draws the open picker (`::picker(select)`) as an attached dropdown: in the top layer, anchored to the select by name (`anchor-name: --theme-select` on the select, `position-anchor` on the picker; an unnamed `anchor()` finds no anchor in newer Chrome), its left edge on the select's left edge, just under the select (flipped above when there is no room), at least as wide as the select. One option per row; the focused option is the active row (`createTitleScreen` moves the focus to the option under a mouse or pen), and `option::checkmark` marks the current Theme at the right of its row. A white sheet with ink-block rows and a pixel check in Paper, a panel with pads, Hot Copper, and a pixel check in Board, a pulp slip with a double ink rule, inked rows, and an ink tick in Dungeon. Elsewhere the OS draws the picker, and the options take the colors of the page.

## Pause Menu look

`src/game/pause-menu.ts` builds one markup for every Theme. Paper and Board show it as the board panel; Dungeon restyles the same elements as the Adventure Sheet in the last section of `src/game/pause-menu.css` (boxed fields with their names on the box edge, tick boxes, ink focus rings). `.pause-menu__fields` is `display: contents` outside Dungeon, so the Paper and Board layout does not change. The shell opens the menu with the Bugs fixed and the Bug total from `game.state()` (`pauseMenu.open({ fixed, total })`); the Bugs fixed field (only in Dungeon) ticks one box per fixed Bug and is hidden when the Level has no Bugs.

## Exhibit Panel look

`src/game/exhibit-panel.ts` and `src/game/resume-prompt.ts` build one markup for every Theme. Dungeon shows the Exhibit Panel as a gamebook page (a numbered section between double rules, Close with an `Esc` key) and "Click to resume" as a pulp slip; the rules are the last section of `src/game/exhibit-panel.css` and `src/game/resume-prompt.css`. The `Sample content` stamp (Dungeon only) marks the sample Exhibits, in the panel foot (`.exhibit-panel__sample`) and at the end of the Skip View lede (`.skip-sample`): remove both when the real Content lands. On touch screens the base hover rules still apply in Dungeon, so the Dungeon section undoes them and inverts only inside `@media (hover: hover) and (pointer: fine)`.

## Skip View look

`buildSkipView` writes one markup for every Theme. Dungeon shows it as the whole book: a pulp page column (`.skip-sheet.dungeon-pulp`) on the green cover, each Exhibit a numbered section (`.skip-section-number`, `.skip-section-kind`), with a running head and an end line (all `.only-dungeon`). The per-look values are the `--sv-*` tokens of `src/skip-view/skip-view.css`; the Dungeon tokens and rules are its last section ("Dungeon: the whole book"). The section number uses a `<span>`: a Skip View test asserts that `main` has no `<b>`.

## HUD look

The HUD colors of an art set include two that can be `null`: `crosshairOutline` (no outline) and `tally` (no Bug tally). The dungeon art set draws the HUD as a pulp strip in ink, with one tick box per Bug in the BUGS FIXED section; the machine art set sets both to `null`, so its HUD does not change. `game.changeArtSet` builds a new HUD, because the layout and the colors are fixed when the HUD is created.

## Analytics

`src/analytics/analytics.ts` holds the GoatCounter site code (`GOATCOUNTER_SITE`), the script tag, and `track(event)`. `track` uses optional chaining and a `try`, so a blocked script never throws. Events: `new-game` and `skip` (Title Screen), `theme/<id>` (a choice in the Theme select of the Title Screen and the Theme switch of the Pause Menu), `exhibit/<id>` and `all-bugs-fixed` (Game core, through the `track` option of `createGame`; `all-bugs-fixed` goes once per visit).

## Sound

`src/audio/audio.ts` is the Audio: the sound effects of the art set through Web Audio, no music. Manual test only. The Game core never touches Web Audio: it reports sound events (`shot`, `door-open`) through the `sound` option of `createGame`, and the browser shell passes them to `audio.play`. In `onNewGame`, the Title Screen creates the Audio with the art set of the shown Theme (`createAudio(baseUrl, artSet)`) and calls `audio.start()`, which creates the `AudioContext` and loads the WAVs from the sounds folder of that art set then, not before. `audio.changeArtSet(artSet)` loads the WAVs of another art set (once, then from a cache) and plays the old sounds until they are loaded; mute stays. Add a new event to `SoundEvent`, map it to its WAV in the `sounds` of each art set in `src/game/theme.ts`, and add its synthesis to `scripts/machine-art/sounds.ts` and `scripts/dungeon-art/sounds.ts` (the helpers are in `scripts/art-kit/synth.ts`). M and the Pause Menu sound setting are the same saved setting (`sound` in `src/game/settings.ts`, through `pauseMenu.toggleSound()`); M mutes all sound through the master gain. A sound that fails to load is loaded again on the next `start()` or change to its art set.
